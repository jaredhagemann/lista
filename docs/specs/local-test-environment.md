# Local Test Environment

## Problem

RLS integration tests currently run against the production Supabase instance. This causes several issues:

- Test users, teams, and orgs accumulate in the production database when cleanup fails or is incomplete
- Auth rate limits on the production instance slow down test runs and cause flaky tests
- There is no safeguard preventing tests from running against production accidentally
- Every test run generates real auth traffic and storage usage against the live project

---

## Goals

- RLS tests run against a fully isolated, local Supabase instance
- Tests cannot accidentally target production
- CI runs the local stack automatically before executing tests
- The local schema stays in sync with production via the migrations in `supabase/migrations/`

---

## Approach: Supabase Local Dev Stack

Supabase provides a first-class local development stack (`supabase start`) that runs Postgres, GoTrue (auth), PostgREST, and Storage in Docker. The RLS tests point at this local instance instead of production.

### Setup

```bash
# Install Supabase CLI
brew install supabase/tap/supabase

# From the project root — spins up the local stack
# Outputs a local URL (http://127.0.0.1:54321) and local anon/service keys
supabase start
```

Migrations in `supabase/migrations/` are applied automatically on start. The local instance is fully isolated — it can be reset at any time with `supabase db reset`.

## Implementation Plan

### 1. `supabase/config.toml`

Run `supabase init` if `config.toml` does not exist. This generates the local project config. Commit it to the repo.

### 2. Local env file for tests

Create `.env.test.local` (gitignored) with the local Supabase credentials output by `supabase start`:

```env
NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:54321
NEXT_PUBLIC_SUPABASE_ANON_KEY=<local-anon-key>
SUPABASE_SERVICE_ROLE_KEY=<local-service-role-key>
```

Update `tests/rls/helpers.ts` to load `.env.test.local` instead of `.env.local`:

```ts
dotenv.config({ path: ".env.test.local" });
```

### 3. Production safeguard

Add a guard at the top of `tests/rls/helpers.ts` that aborts if the configured URL points at production:

```ts
const url = process.env.NEXT_PUBLIC_SUPABASE_URL ?? "";
if (!url.includes("127.0.0.1") && !url.includes("localhost")) {
  throw new Error(
    "RLS tests must run against a local Supabase instance. " +
    "Set NEXT_PUBLIC_SUPABASE_URL to http://127.0.0.1:54321 in .env.test.local."
  );
}
```

### 4. `vitest.config.ts` update

Point the RLS test config at `.env.test.local`:

```ts
// vitest.config.rls.ts (or update existing config)
export default defineConfig({
  test: {
    envFile: ".env.test.local",
  },
});
```

### 5. `package.json` script update

```json
"test:rls": "supabase db reset && vitest run tests/rls"
```

`supabase db reset` re-applies all migrations from scratch before each run, ensuring a clean slate.

### 6. CI (GitHub Actions)

Add a step before `pnpm test:rls` to start the local Supabase stack:

```yaml
- name: Start Supabase local stack
  run: supabase start

- name: Run RLS tests
  run: pnpm test:rls
```

The local keys are stable and deterministic (same for every project using the default config), so they do not need to be stored as CI secrets.

---

## Tradeoffs

| Approach | Pros | Cons |
|---|---|---|
| **Local Supabase** (this spec) | Fully isolated, fast, free, no rate limits | Requires Docker; migration sync discipline required |
| **Separate staging Supabase project** | Closer to prod environment | Costs money; still shared state between developers |
| **Keep using prod + fix cleanup** | No new infra | Auth rate limits; test noise risk; cleanup failures pollute production |

### Day-to-day usage

```bash
supabase start      # start the local stack (fast after first run; Docker must be running)
pnpm test:rls       # reset DB + run all RLS tests
supabase stop       # stop when done
```

### Notes on local stack setup

- `supabase start` outputs JWT keys as `ANON_KEY` / `SERVICE_ROLE_KEY` (run `supabase status -o env` to see them). These must match what's in `.env.test.local`.
- `edge_runtime` and `realtime` are disabled in `config.toml` — they are not needed for RLS tests and caused startup failures (edge runtime tries to fetch Deno imports that aren't available in Docker's network).
- `supabase db reset` always restarts containers after applying migrations. Using `--db-url` with the direct postgres connection string avoids restarting stopped/disabled containers.
