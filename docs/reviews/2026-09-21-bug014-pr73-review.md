# BUG-014 / PR #73 review — September 21, 2026

**Recommendation: request changes. BUG-014 is not fully resolved, and this is not yet a scalable pagination design.**

Reviewed [PR #73](https://github.com/jaredhagemann/lista/pull/73), commit `efd98f25f46bd211f2fc9a12660251e585d72e66`, against `34bfc3ce5`. Application code was not changed. The useful parts are the shared batching helper, bounded availability queries, and explicit error handling instead of displaying failed reads as empty lists. The accepted decision to retain calendar preloading is respected here. However, the PR's own completeness test failed in this review, and new UI window navigation can misrepresent and overwrite saved availability.

## Findings to address before approval

### 1. P1 — Pagination lacks a unique ordering and still silently drops responses

Locations: [availability query](C:/Users/jared/Projects/lista/apps/web/src/app/dashboard/availability/page.tsx:77), [club member query](C:/Users/jared/Projects/lista/apps/web/src/app/dashboard/club/members/page.tsx:113), and [schedule query](C:/Users/jared/Projects/lista/apps/web/src/app/dashboard/schedule/page.tsx:38).

Availability orders only by `event_id`, so all players responding to the same event tie. Schedule orders only by `start_time`, where simultaneous events tie. Club memberships have no database ordering at all; sorting the accumulated result afterward cannot repair omitted rows.

**Observed:** the PR's unchanged `tests/rls/paged-fetch.test.ts` returned 1,050 rows but only **1,049 distinct `(event_id, profile_id)` pairs**. Its uniqueness assertion at line 94 failed. A response was duplicated and another omitted despite a successful load, recreating the original false “no response” defect. This occurred without the concurrent-deletion probe running at the same time; files were executed sequentially.

Require a deterministic, unique order for every paginated query: for example `(event_id, profile_id)` for responses, `(start_time, id)` for events, and membership `id` for raw membership batching. Do not fix this by deduplicating the final array: that cannot recover the skipped row. PostgreSQL explicitly requires a unique ordering for predictable LIMIT/OFFSET subsets. [PostgreSQL documentation](https://www.postgresql.org/docs/current/queries-limit.html).

### 2. P1 — Changing availability windows can overwrite an existing response

Location: [matrix props](C:/Users/jared/Projects/lista/apps/web/src/app/dashboard/availability/page.tsx:139), interacting with [state initialization](C:/Users/jared/Projects/lista/apps/web/src/components/availability/availability-matrix.tsx:180).

The new links change the server-fetched events and `initialRows`, but the matrix remains the same client component. Its `statusMap` reads `initialRows` only when initialized. Responses for events newly introduced by “Whole season” are therefore absent from the map.

**Reproduced with the actual component:** render an upcoming event, then rerender with an additional event 200 days away whose saved response is `unavailable`. That event displays “No response.” Clicking bulk Available and confirming calls the existing upsert with `available` for this already-answered event. The dialog promises previously answered events will be unchanged.

Reconcile response state with each loaded window, or remount the matrix using the relevant team/profile/window identity. Include navigation and bulk-action coverage; testing only the server query misses this defect. The reproduction tests React prop updates, not a full browser navigation session.

### 3. P2 — “Past 30 days” initially hides every event it loads

Location: [window integration](C:/Users/jared/Projects/lista/apps/web/src/app/dashboard/availability/page.tsx:136), interacting with [the matrix's time filter](C:/Users/jared/Projects/lista/apps/web/src/components/availability/availability-matrix.tsx:173).

The matrix still defaults to `timeFilter = "upcoming"` and filters out past events. The new Past window supplies only past events. Rendering a past event through the real component displays **“No events found.”** Users must discover the second time filter and switch it to All events. Whole season also initially hides its historical portion.

Make the server window the single source of date filtering, or explicitly coordinate the client filter with it. Remounting for finding 2 alone does not fix this: it initializes Upcoming again.

### 4. P2 — Row batching leaves an unbounded request URL

Location: [availability event-ID filter](C:/Users/jared/Projects/lista/apps/web/src/app/dashboard/availability/page.tsx:76). Club memberships use the same pattern for team IDs.

Every response page puts the entire window's event IDs into one GET `.in(...)` filter. Paging the returned rows does not limit that URL.

**Observed against the local gateway:** 50 and 200 UUIDs succeeded; 300, 500, and 1,000 UUIDs returned **HTTP 414, URI too long**. This does not require a large response table: even querying nonexistent UUIDs fails at the gateway. The two-year Season window can reasonably exceed 300 events. The production threshold remains unverified.

Filter responses through a database join to events using team/date criteria, use a suitably authorized RPC, or chunk the ID filter separately from row pagination. Any chunked implementation must preserve error handling and account for the aggregate row budget. Add coverage with hundreds of event IDs; the current 50-event fixture cannot expose this limit.

### 5. P2 — OFFSET batching silently skips rows when records change between requests

Location: [pagination loop](C:/Users/jared/Projects/lista/apps/web/src/lib/supabase/fetch-all-rows.ts:45).

A unique order fixes finding 1 for a static dataset, but each offset request sees a potentially different dataset. Removing a previously fetched row shifts the next offset past a still-existing record.

**Reproduced locally:** create 501 events with distinct start times, fetch the first 500, delete the first fetched event, then fetch offset 500. The helper returns successfully, includes the deleted event, and omits the final event that still exists. No `PartialFetchError` is raised. Availability rows can similarly shift when a player clears a response during a multi-request load.

Use keyset pagination with an explicit unique cursor to avoid offset shifting, or read the bounded result through a database operation with an appropriate consistency contract. Keysets alone do not provide a point-in-time snapshot when ordering keys or responses are edited; define whether live consistency is sufficient or whether the UI needs snapshot/version handling. A final count or deduplication pass is not a complete solution.

## Assessment of extensibility and scale

The helper is a **fetch-everything utility using batches**, rather than UI pagination. It reduces the per-response size, but each page load still retrieves and retains all matching rows. Before the 20,000-row guard trips, one dataset can require 40 serial database requests. Larger offsets also require PostgreSQL to compute skipped rows. [PostgreSQL documentation](https://www.postgresql.org/docs/current/queries-limit.html).

The calendar preload is an explicitly accepted interim choice. It should be described as such, with these limits tracked rather than presented as the long-term pagination architecture:

| Area | Current limitation | Recommended direction |
| --- | --- | --- |
| Availability | Loads up to two years of responses before displaying 10 events; state and date filters conflict | Fetch a bounded event page/window and its responses; use stable identities and a consistent window state |
| Calendar | Fetches all event history before rendering even the default List tab, which performs its own pagination | Eventually load visible calendar dates with modest adjacent-window prefetch; let the List tab load independently |
| Club members | Fetches all membership rows, then groups, searches by name, sorts, and renders in application code | Page distinct people at the database boundary, preserving all required membership summaries and filtering/sorting semantics |
| Club scope | Initial active-team lookup is still unpaginated and its error is ignored | Use an organization-scoped join/RPC instead of relying on a complete client-side team-ID list; otherwise page and validate this prerequisite too |
| Errors and limits | Error pages remove the window/filter controls but instruct users to narrow the date range | Preserve recovery controls; distinguish query failures from an exceeded size budget |
| Shared API | Callback accepts arbitrary offset queries with no ordering or completeness contract | Provide a typed page/cursor result and query-specific ordering/filter ownership; retain fetch-all only for deliberately bounded reads |

For the cursor queries, evaluate indexes matching scope, ordering, and joins with authenticated `EXPLAIN`/timings on representative data. An events index beginning with team and ordered time/ID is a candidate, not a verified performance fix. This PR introduces no supporting migration or authenticated scale benchmark.

Two smaller helper-contract issues should be documented/tested before broad reuse: a short page is a reliable termination signal only when the requested page size is no larger than the API cap, and the current guard rejects exactly 20,000 rows without probing whether more exist. With custom limits not divisible by the page size, a final short page can also return more than `maxRows`. The configured 500-page/1,000-cap combination is valid today; claims that the helper is independent of the API cap are too broad.

“Whole season” is also a rolling year before/after now, not the team's actual season. That is documented in the implementation, so this review treats it as an explicit limitation rather than inferring a new product decision. Clarify the label or connect it to actual season dates before depending on it for historical completeness.
