## 1. P1 — Serialize the role-editor trigger against removal of a directorship

Source: [new trigger, lines 22–29](https://github.com/jaredhagemann/lista/blob/ff195e6b4e22a307f833f52770456d578cb6c74a/supabase/migrations/20261105000001_director_role_needs_directorship.sql#L22-L29).

The trigger checks `organization_members` with an ordinary `NOT EXISTS` read. Unlike `remove_team_member_role`, it takes no lock on the qualifying directorship. The newly exposed role editor writes `team_members.role` directly, so it bypasses the RPC's `FOR SHARE` protection.

**Reproduced with two PostgreSQL sessions on an active Club plan:**

1. Give a director a `player` membership on the team.
2. Begin a transaction, run the real `remove_org_director`, and pause before commit. Its directorship deletion is uncommitted, and its roster cleanup has retained the player's row.
3. As the owner, perform the same authenticated `UPDATE team_members SET role = 'director'` as the new role editor. The trigger sees the still-visible, uncommitted-deleted directorship and permits the update.
4. Commit the removal transaction.

**Observed:** the directorship is absent, the team membership is `director`, and `is_team_admin(team_id)` still returns true for the removed director. Both writes succeeded. This leaves administrative access that club removal should have revoked; before this edit the retained team role was only `player`. P1 because it is a reproduced authorization defect requiring a prior directorship and overlapping operations.

**Requested change:** coordinate every transition to `director` with directorship removal, including direct role-editor writes, using a consistent locking strategy. After the two operations finish, the result must correspond to a valid serial ordering: either the role edit happens first and removal deletes the director row, or removal happens first and the edit is refused. Add an overlapping-transaction regression test, not only the existing sequential role tests.

## 2. P2 — Preserve standalone free-team owner behavior

Sources: [new club-admin helper, lines 14–24](https://github.com/jaredhagemann/lista/blob/ff195e6b4e22a307f833f52770456d578cb6c74a/apps/web/src/lib/club/club-admin.ts#L14-L24) and [RPC directorship lookup, lines 49–60](https://github.com/jaredhagemann/lista/blob/ff195e6b4e22a307f833f52770456d578cb6c74a/supabase/migrations/20261105000000_remove_team_member_role.sql#L49-L60).

Both checks equate any organization-owner record with a club directorship. The real `create_team` function also creates an organization-owner record for a standalone free team. The [architecture spec](../specs/multi-tenant-architecture.md) explicitly describes free-user owner entries as record keeping, with no UI change for them.

**Reproduced through the real `create_team` RPC:** the newly created organization has `plan = 'free'`, but `isClubAdminOfTeam` returns true and `remove_team_member_role` returns `kept_as_director`. Consequently the member page offers Director for the free-team owner, and another admin's Remove action reaches the new early return instead of the existing "Transfer ownership before removing the team owner" guard. The owner becomes Director, and subsequent removal guidance points to club settings.

**Requested change:** distinguish actual club-director behavior from the standalone team's record-keeping owner entry, consistently in the UI helper and database decision. Retain the free-team owner's existing removal guard and ordinary role options. Cover a standalone team created through the actual product RPC rather than constructing only an organization-members row.

## 3. P2 — Make club team creation compatible with the new bulk-insert guard

Sources: [new trigger, lines 20–31](https://github.com/jaredhagemann/lista/blob/ff195e6b4e22a307f833f52770456d578cb6c74a/supabase/migrations/20261105000001_director_role_needs_directorship.sql#L20-L31) and its existing caller [POST /api/club/teams, lines 109–130](https://github.com/jaredhagemann/lista/blob/ff195e6b4e22a307f833f52770456d578cb6c74a/apps/web/src/app/api/club/teams/route.ts#L109-L130).

The team-creation API reads all directors before creating the team and then bulk-inserts that earlier snapshot. If one director leaves between the read and the insert, the new trigger raises `NOT_A_CLUB_DIRECTOR` for that stale person. The whole bulk insert rolls back, including the valid owner's enrollment. The route treats enrollment failure as nonfatal and returns 201.

**Reproduced with the actual POST handler and local PostgreSQL:** the test lets a real `remove_org_director` commit immediately after the handler's real organization-members read. All other table operations use the real local client; only request authentication and cookie saving are stubbed. The handler logs the trigger exception and returns `{ ok: true, teamId }` with HTTP 201, but the new team has **zero** roster memberships, including no creator row. Normal team switching requires a membership row, so the creator cannot select the supposedly successful new team through that path.

This is distinct from finding 1: here the directorship removal commits *before* the enrollment write. Locking the trigger's read does not repair the route's stale list or its success response after failed enrollment.

**Requested change:** make team creation and enrollment use a coherent, transactional view of current directors, or safely recover stale-list enrollment failures. Do not return successful creation with the creator unenrolled. Add coverage for director removal between membership discovery and enrollment.
