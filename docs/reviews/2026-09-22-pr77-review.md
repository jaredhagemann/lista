## 1. P2 — A failed write strands the queued choice as permanently unsaved state

Location: `apps/web/src/components/availability/availability-matrix.tsx:419–421`, together with the chain deletion at line 411.

Reproduction: click an unanswered cell to Available and then Maybe while the Available request is pending; let Available fail. The error branch deletes the write chain, so the queued Maybe is never sent. The new rollback guard preserves the overlay because Maybe differs from the failed request's Available status. That overlay retains `settledTick: null`, so neither the recovery read nor a subsequent successful Refresh removes it.

The result is a persistent Maybe chip even though the database has no response. This is introduced by the rollback change in this PR; before that change, the failed chain's overlay was removed.

Either continue processing the newest queued intent through the serialized chain, or explicitly abort that intent and remove its optimistic state before revalidating. A newer overlay must not survive after the only write chain that could persist it has been discarded. Preserve isolation between unrelated cells and the context-switch ordering fixed in this PR.

**Controlled component probe:** only the first upsert is sent; it fails; repository recovery and Refresh both return an empty response set; the chip remains Maybe. The desired assertion that the rendered value agrees with the persisted result fails.

## 2. P2 — An uncertain bulk outcome permits retry before revalidation finishes

Location: `apps/web/src/components/availability/availability-matrix.tsx:511–519`; the action's only disabled condition is `bulkBusy` at line 646.

`runBulk` clears `bulkBusy` and closes the confirmation as soon as the RPC returns an error. The replacement page read is merely scheduled afterward. While that read is pending, `failure` is still null and the bulk buttons are enabled. The error message also states that the page has been read again before that has happened.

Reproduced by returning an RPC timeout and holding the subsequent response read unresolved: the Available bulk button is immediately enabled. The user can submit another operation while viewing pre-operation responses, including a different requested status, without seeing what the uncertain first operation committed. Conflict-ignore protects existing rows but does not make that retry an informed confirmation of the outcome. Spec section 8.2 explicitly requires revalidation before offering retry.

Retain a recovery state until the relevant page revalidation completes, disable new bulk submissions during that state, and keep them unavailable if recovery fails until a successful retry of the read. Announce completed revalidation only after it succeeds. Ensure that recovery completion belongs to the intended context.
