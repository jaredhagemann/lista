## Verdict

The implementation addresses the principal BUG-010 requirements: event-owned timezone, team defaults, event-local forms and labels, notification/reminder timezone selection, inclusive recurrence boundaries and preserving existing instants during backfill. Mobile display support is included as requested. Three reproduced edge cases remain; address these before treating the ticket as fully fixed.

## Findings

### 1. [P2] A timezone exception becomes the timezone of the entire series editor

Location: `apps/web/src/components/calendar/event-detail.tsx:782`.

`zone` belongs to the opened occurrence, but is passed as the series' original timezone. The planner uses that zone to compare all occurrences with the floating DTSTART pattern. For a Thursday 16:00 Denver series, edit one occurrence to 16:00 Los Angeles, then open an entire-series title edit from that occurrence. Regular Denver siblings now appear at 15:00 in the supplied zone and are incorrectly classified as time exceptions. The local planner reproduction updated only the Los Angeles exception and skipped the regular upcoming siblings.

Resolve the recurrence pattern's timezone independently of the opened occurrence. Preserve that pattern metadata if the head itself is edited as a single occurrence; merely changing the caller to use the mutable head timezone does not handle that case. Cover edits opened from a timezone exception and from a individually modified head. Opening a regular occurrence is a workaround for the reproduced child case.

### 2. [P2] Saving an untouched event can shift its instant during the fall overlap

Location: `apps/web/src/components/calendar/event-detail.tsx:190-191`.

Both timestamps are always reconstructed from minute-only wall-clock inputs. The conversion deliberately picks the earlier reading of an ambiguous time, losing which occurrence of that hour the original timestamp identified. A component test opened a Denver event at `2026-11-01T08:15:00Z` (01:15 MST, the second 01:15), clicked Save without changing anything, and captured an update to `2026-11-01T07:15:00Z` (01:15 MDT). The end moved too. This can affect existing/backfilled events and also marks a metadata-only edit as a scheduling change, triggering notifications.

Retain the original timestamp when its wall-clock input and effective timezone have not changed. Apply disambiguation only when the user actually changes the time or zone. Test both start and end in the repeated hour.

### 3. [P2] The conversion's offset sampling fails for Auckland DST transitions

Location: `apps/web/src/lib/events/event-timezone.ts:193-199`.

Sampling twelve hours either side of the naive UTC wall clock does not always straddle the actual local transition in UTC+12/+13 zones. Both samples can use the post-transition offset. Reproduced results for the supported `Pacific/Auckland` zone:

| Input | Expected by the helper's documented policy | Actual |
| --- | --- | --- |
| 2026-09-27 02:30, spring gap | 03:30 local / 2026-09-26T14:30Z | 01:30 local / 2026-09-26T13:30Z |
| 2026-04-05 02:30, fall overlap | Earlier occurrence / 2026-04-04T13:30Z | Later occurrence / 2026-04-04T14:30Z |

Use offset discovery that covers the actual candidate instants across the supported timezone range, or a timezone conversion implementation with explicit disambiguation. Add both tests beyond the existing North American DST cases. This helper affects single events and recurrence expansion.
