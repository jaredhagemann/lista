# PR #80 — BUG-015 webhook delivery review

**Recommendation: request changes.** Reviewed [PR #80](https://github.com/jaredhagemann/lista/pull/80), head `21bcf154601e5a5eaacaeabacf47fd6fbc3869fd`, against `fc79e3246`.

The checked invoice/subscription-update writes now withhold acknowledgement when Supabase returns an error, and sequential completed-event replays are deduplicated. However, the ticket's acknowledgement, ordering, and duplicate-delivery guarantees are not yet satisfied across the route. Seven controlled route probes reproduce four findings.

## 1. P1 — Three writes still acknowledge failures and are recorded as completed

Locations: `apps/web/src/app/api/billing/webhook/route.ts:209`, `:395`, `:452`; completion at `:91`.

The terminal cancellation write and both checkout helpers still call `await admin.from(...).update(...)` directly. They do not use `mustWrite` or inspect the returned error. These are three of the seven writes the PR claims to have checked.

**Reproduced separately for all three branches:** Supabase returns a constraint-style error, no organization change commits, the route returns 200, and delivery processing reaches the completion ledger. A subsequent replay will now be skipped as completed. For subscription checkout this leaves paid activation unapplied; for deletion it leaves the club's old billing state; for setup it can leave the customer association unpersisted.

Route every required write through the checked path and only complete an event after its required work succeeds. Add failures for every event branch, not only `invoice.payment_succeeded`. Also inspect errors on required organization reads: the subscription checkout lookup currently treats a failed read like an absent/ineligible organization and returns normally, which can also result in a completed ledger entry without activation. That read case was inspected statically, not included among the seven probes.

## 2. P1 — The shared strict timestamp guard discards legitimate billing updates

Locations: `apps/web/src/lib/billing/webhook-ledger.ts:73–74`; route state updates at `:185`, `:294`, `:317`.

There are two failures in using one organization-wide event timestamp as the version of several partial updates:

- **Equal timestamps are not duplicate events.** Deliver a failed-payment event and then a distinct successful-payment event with the same `created` second. The strict `<` guard drops the success, marks it complete, and leaves the organization `past_due`. Stripe explicitly warns that distinct snapshot events can share a timestamp and that `created` must not determine event order or whether an event was processed. See [Stripe event ordering](https://docs.stripe.com/webhooks#event-ordering) and the [event timestamp definition](https://docs.stripe.com/api/events/object).
- **Newer partial updates do not supersede every older field.** Deliver an invoice failure at 12:00, then a delayed subscription tier update from 11:00. The invoice writes only status but advances the same timestamp; the tier update is skipped, leaving `club_small` instead of `club_large`. The invoice never supplied a replacement plan, so dropping the tier event loses information. Both route calls return 200.

Both cases are reproduced by the probes using the existing test's filter-aware database double. Reconcile a coherent current provider state with appropriate per-resource serialization, or design a scoped versioning/reconciliation mechanism that handles independent fields and same-second events. Changing `<` to `<=` alone does not resolve independent-field loss or determine the order of same-second snapshots. Event IDs identify replays but must not be invented into a chronological tie-breaker.

## 3. P1 — Cancellation does not participate in the new ordering protection

Locations: `apps/web/src/app/api/billing/webhook/route.ts:209–224` and `:294–296`.

`customer.subscription.deleted` neither records `stripe_event_at` nor checks the new ordering condition. The new guards therefore do not know that terminal cancellation is the newest state.

**Reproduced:** process deletion at 12:00, which sets `subscription_status = canceled`; deliver a delayed successful-payment event from 11:00. Since the stored watermark remains null (or predates the payment), the guarded invoice write succeeds and changes status back to active. The organization now combines a Free downgrade with an active subscription badge, contrary to the stated terminal lifecycle. The deletion and checkout/schedule paths also remain outside the broader ordering strategy described in the ticket.

Include terminal cancellation and all relevant lifecycle writers in the reconciliation strategy, with subscription/schedule identity checks where needed. Do not treat the two-invoice ordering test as proof that cancellation and activation transitions are protected.

## 4. P2 — An incomplete ledger entry is not an exclusive processing claim

Location: `apps/web/src/lib/billing/webhook-ledger.ts:47–54`.

For a duplicate whose first delivery is still running, `completed_at` is null, so `claimStripeEvent` returns `process` to both requests. It cannot distinguish an abandoned attempt from a live one. Both handlers proceed to the email call, including the handler whose organization update matched no rows because of the timestamp guard.

**Reproduced:** run two `POST` calls concurrently for one invoice event ID. Both process the event and the email mock is invoked twice. This requires no database error or failure of the completion write, so it is separate from the explicitly deferred post-email/pre-completion crash window.

Use an atomic processing claim with a lease/recovery mechanism, or serialize processing so only one live handler owns an event. A competing request must not acknowledge unfinished work unless durable processing responsibility exists. Keep recoverability for an attempt that dies before completion, and add an overlapping-delivery test rather than only sequential replay coverage.
