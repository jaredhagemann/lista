## 1. P2 — Explain the actual continuation query before claiming flat deep paging

Location: `tests/scale/pagination-scale.test.ts:305–315`.

The test named "starts the event scan at the cursor" contains no cursor predicate. It explains the first eleven events after `now()`, not page 21. The separate page-21 test only asserts the returned row count equals page one's count; an offset query or a cursor query that scans and discards earlier rows could satisfy that assertion too.

The repository's continuation includes both `start_time >= cursor.startTime` and the composite time/ID OR predicate. Neither appears in this EXPLAIN. In my run its index condition was the team plus the initial date window, confirming that the harness did not exercise a deep start condition. The verification document nevertheless attributes its plan to a keyset continuation and claims bounded rows scanned.

Capture a real continuation cursor, explain the equivalent authenticated query including its filters and projection, and assert the cursor's index condition and bounded scan/filter work. Prefer checking the repository-generated query so the test detects removal of the extra lower bound that prevents the known scan-from-window-start regression. Update the published plan and conclusion to match the measured query.

## 2. P2 — Complete the section 13 measurements before declaring stage 5 verified

Location: `docs/reviews/2026-09-22-pagination-scale-verification.md:43–50`, together with the single fixed-size fixture in `tests/scale/pagination-scale.test.ts`.

Section 13 requires comparisons at 1,000, 10,000, and 100,000 historical events while holding the visible page/month constant, plus authenticated request counts, payloads, view-ready timings, and retained cache entries. The harness runs only a 100,000-total-event fixture. It calls event-page/response/roster repositories but never the calendar range reader or calendar cache. It measures the size of the final serialized return value rather than network request counts or total transferred bytes. No view-ready or retained-cache measurement is recorded.

These are useful completeness checks, but they cannot establish the calendar/cache and growth claims presented as completed structural verification. In particular, the calendar bullet is supported by existing component behavior tests, not a calendar measurement on the scale fixture.

Add the missing comparative runs and calendar/request/cache measurements, with actual query/request counts rather than inferring cost from returned row counts. Record the required navigation and staging verification or explicitly leave those release criteria outstanding instead of marking the final stage complete. No arbitrary latency SLA or authorization redesign is needed.

## 3. P2 — Clean up dependencies before deleting the fixture account, and surface cleanup failures

Location: `tests/scale/pagination-scale.test.ts:113–124`.

The hook tries to delete the auth user before deleting the organization and events. Every seeded event uses that user's profile as `created_by`; the local schema confirms `events_created_by_fkey` references `profiles(id)` without a delete action. Deleting the user cascades to the profile and is blocked by those event references. The SDK deletion result is ignored, so the hook proceeds without reporting that failure.

After my run, the organization and seeded roster profiles were gone, but the `scale-check@fixture.local` auth user remained. The suite also exited 1 because this cleanup hook exceeded its 120-second timeout, despite all eight assertions passing.

Delete dependent fixture data before the caller account, use the recorded `authUserId` instead of searching one page of users, and check SDK errors and SQL exit status. Ensure cleanup has a measured, workable time budget or reduce its cost. Apply the same dependency ordering to interrupted-run recovery in `beforeAll`, which also deletes the old account before replacing its dependent fixture. A verification command must not report success while leaving fixture identities behind.

I removed the leftover account through the local Auth admin API after verifying its fixture email and that the seeded organization/profiles had been removed. No production or staging data was touched.
